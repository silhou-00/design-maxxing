Video Scrub

Scroll position drives which frame of a real sequence is shown. 48 frames, 214 KB, and not one line of JavaScript.

Binding scrubbed Mechanism stacked frames, one view() slice each Cost high — the asset is the cost Risk high

This is a real asset. Forty-eight WebP frames of a machined part on a turntable, rendered to disk and shipped — 214 KB, about 4.5 KB a frame. Scroll the stage below and the sequence scrubs.

It also runs on no JavaScript at all, which the technique doc did not expect. Each frame is stacked and given its own one-forty-eighth slice of a view() timeline with steps(1). Frames turn on in order, later ones painting over earlier ones, and turn off again in reverse when you scroll back up.

48 frames · 214 KB · CSS only

The asset is still the cost. That is the honest lesson and it has not changed: this sequence is small because the subject is simple and procedurally rendered. Real footage at this frame count runs to megabytes, and that is before anyone asks for retina.

Why a sequence beat the video here. A normally-encoded video seeks only to keyframes, so a scrub lands on the nearest one and stutters. Encoding for scrub — a keyframe every frame or two — can multiply the file size past what the sequence costs. And a sequence needs no JS, because there is no currentTime to set.

Flat rates this ✗, and the reasoning is exact: the heaviest possible payload, in the style whose entire pitch is lightness.

The craft

Frames turn on, they do not cross-fade. Each frame gets a hairline slice of the timeline and steps(1,end), with fill: both. Before its slice it is transparent; after it, opaque. Later frames sit above earlier ones in the DOM, so the newest visible frame wins — and scrolling back up switches them off in reverse.

The slice is computed, not written 48 times. --slice: calc(100% / var(--n)) and an inline --i per frame. Adding frames is a count change, not a rewrite.

This turned out not to need JavaScript. The technique doc assumes JS because currentTime is a media property no CSS can reach. A frame sequence has no currentTime — so it runs entirely on the compositor, which is strictly better than the documented approach.

First frame eager, the rest lazy. Otherwise 48 requests fire before anything paints.

The timeline belongs to the tall wrapper, not the frames. The frames sit inside a sticky stage that never traverses the viewport, so their own view() progress never advances — the animation registers, reports running, and shows frame zero forever. This is the same failure as putting view() on a fixed parallax layer, and it is the single most common way a CSS scrub silently does nothing.

Implementation

.wrap{                                /* the TALL element owns the timeline */
  --n:48; --slice: calc(100% / var(--n));
  height: 340vh;
  view-timeline-name: --scrub;
  view-timeline-axis: block;
}

.fr{                                  /* every frame, stacked */
  position:absolute; inset:0; opacity:0;
  animation: show auto steps(1,end) both;
  animation-timeline: --scrub;        /* NOT view() — the frames never move */
  animation-range:
    contain calc(var(--i) * var(--slice))
    contain calc((var(--i) + 0.001) * var(--slice));
}
@keyframes show{ to{ opacity:1 } }

<!-- <img class="fr" style="--i:0"> … --i:47 -->

@supports not (animation-timeline: view()){
  .fr{ opacity:0 } .fr:first-child{ opacity:1 }   /* poster, never a blank box */
}

When not to use it

  • In flat — it rates ✗: the heaviest payload in the style whose pitch is lightness.
  • On mobile data without a poster-only fallback.
  • With every frame eager-loaded — 48 parallel requests before first paint.
  • As decoration. If the footage is not the content, the payload is not justified.

Style packs

⚠ everywhere it is permitted, ✗ for flat and brutalism. ○ for minimalism — this is Apple's model, and it is what makes "Apple does video scrub inside a minimal shell" coherent rather than contradictory. Confirm the asset budget before proposing it.
